⏺ 好问题。当前顺序是先 Decision 评估，后安全/缓存/Memory，这是刻意的设计选择。核心原因：

  这些检查都是 per-Decision 配置的

  从源码可以看到：

  ┌───────────┬─────────────────────────────────────────────────┬────────────────────────────────────────────────┐
  │   步骤    │               为什么依赖 Decision               │                      证据                      │
  ├───────────┼─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ Jailbreak │ 不同 Decision 有不同阈值和 include_history 设置 │ isPIIDetectionEnabled() 检查 Decision 是否启用 │
  ├───────────┼─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ PII       │ 不同 Decision 可以启用/禁用 PII 插件            │ req_filter_pii.go:39-61 按 Decision 判断       │
  ├───────────┼─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ 缓存      │ 不同 Decision 有不同的相似度阈值和 TTL          │ GetCacheSimilarityThresholdForDecision()       │
  ├───────────┼─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ RAG       │ 不同 Decision 配置不同 RAG 后端                 │ milvus/external_api/mcp 等按 Decision 分发     │
  ├───────────┼─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ Memory    │ 取决于 Decision 是否启用 memory 插件            │ 同理                                           │
  └───────────┴─────────────────────────────────────────────────┴────────────────────────────────────────────────┘

  Decision 是配置的 pivot point — 没有它，你不知道该用什么策略。

  如果放在 Decision 之前会怎样？

  你就只能用全局统一策略：所有请求同一个 jailbreak 阈值、同一个缓存规则。这丧失了"不同场景不同安全等级"的灵活性（比如医疗问答 Decision
  用严格阈值，编程助手用宽松阈值）。

  代价是什么？

  恶意请求（最终会被 jailbreak 拦截的）也会先跑一遍 Decision 评估。但 Decision 评估本身很轻量（关键词匹配 + embedding
  计算），而且恶意请求占比很低，所以这个 tradeoff 是值得的。

  一句话总结：先路由再检查，因为"检查什么、怎么检查"本身就是路由决策的一部分。
