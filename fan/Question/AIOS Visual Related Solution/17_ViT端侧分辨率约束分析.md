正在做qwen VL2.5 vit的模型适配和端侧性能测试 目前vit端侧导出不支持512*512及其以上的分辨率 会提示VTCM资源不够用 正在做224*224和448*448的模型适配和端侧性能测试。qwen官方实现图片经过预处理后到了计算图这一步转换成的输入size太大了 比如672*672的分辨率到了计算图就得是2304x1x1x1176 我们的scenarios在对图片的分辨率要求上尽可能把这个因素考虑进去 后边会有前述两个分辨率的latency测试结果



这句话的核心意思是：**Qwen VL2.5 的 ViT 把图片切 patch 后，tensor 尺寸会膨胀得很大，超出端侧芯片的片上内存（VTCM）限制，所以我们规划各场景的输入分辨率时要考虑这个硬约束。**

具体拆解：

### 为什么 672×672 变成了 2304×1×1×1176

```
原始图片 672×672
    │
    ▼ Patch Embedding (patch_size = 14×14)
    │
(672÷14) × (672÷14) = 48 × 48 = 2304 个 patch
    │
    ▼ 每个 patch 投影到 hidden_dim = 1176
    │
Tensor shape: [2304, 1176]  →  reshape 成 [2304, 1, 1, 1176]
```

language- **2304** = patch 数量（图片被切成多少块）
- **1176** = Qwen VL2.5 ViT 的 hidden dimension

### 不同分辨率对应的 tensor 大小

| 输入分辨率 |           Patch 数           |   Tensor Shape   | 大小 (FP16) |
| :--------: | :--------------------------: | :--------------: | :---------: |
|  224×224  |  (224÷14)² =**256**  | 256×1×1×1176 |   ~0.6 MB   |
|  448×448  | (448÷14)² =**1024** | 1024×1×1×1176 |   ~2.4 MB   |
|  512×512  | (512÷14)² ≈**1369** | 1369×1×1×1176 |   ~3.2 MB   |
|  672×672  | (672÷14)² =**2304** | 2304×1×1×1176 |   ~5.4 MB   |

关键：**patch 数量随分辨率呈平方增长**，而 VTCM（片上 SRAM）是固定大小的（高通 Hexagon NPU 通常 2-8 MB），所以分辨率一大就装不下了。

### 对我们场景规划的影响

这句话在提醒团队：**Camera 输出给 ViT 的图片分辨率不能随便定，要以端侧能跑得动为前提**。也就是说之前文档里写的 "1080p / 720p" 是 Camera 采集分辨率，但送进 ViT 之前还要 **resize 到 224 或 448**，这个 resize 后的分辨率才是真正的算力瓶颈。

实际影响：

- **224×224** — 端侧最安全，延迟最低，但细节丢失多（远距离路牌/文字可能看不清）
- **448×448** — 分辨率和算力的平衡点，大多数场景够用
- **≥512×512** — 当前 VTCM 放不下，暂时不可用

所以在规划时，需要明确每个 Head 任务对分辨率的真实需求：粗粒度分类（天气/光照/场景）用 224 就够了，细粒度识别（路牌文字/车牌/规则牌）可能必须 448 甚至需要 FTC 长焦裁剪后再送入。
