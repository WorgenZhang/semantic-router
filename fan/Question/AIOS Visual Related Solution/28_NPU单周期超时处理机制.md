# NPU 单周期超时处理机制

## 核心问题

单周期 100ms 内，CV 和 ViT 模型没有完成所有 camera 流的推理，超过 100ms 后，这些没完成的任务怎么处理？

---

## 结论：分 tier 区别对待

```
┌────────────────────────────────────────────────────────────────────────┐
│ UC Tier          │ 超时处理                                            │
├────────────────────────────────────────────────────────────────────────┤
│ safety           │ 允许溢出到下一周期，必须跑完                        │
│ (preemptible:    │ 但下一周期该 UC 的新任务会被延迟启动                │
│  false)          │ → "宁可下一轮晚开始，也要本轮跑完"                  │
├────────────────────────────────────────────────────────────────────────┤
│ core             │ 本轮未完成的任务直接丢弃（用上轮结果）              │
│ (preemptible:    │ 下一轮按正常周期重新调度                            │
│  true)           │ → "丢一帧不要紧，别拖累下一轮"                      │
├────────────────────────────────────────────────────────────────────────┤
│ enhancement      │ 不可能超时 — 早在调度前就被 disable 了              │
│ (preemptible:    │                                                     │
│  true)           │                                                     │
└────────────────────────────────────────────────────────────────────────┘
```

---

## 具体场景分析

### Safety UC 超时：溢出执行

以文档中优化前的时序为例，SCF_R 的 Backbone_B 完成时间是 118.1ms，超出 100ms 周期 18ms：

```
周期 N                              │  周期 N+1
0ms ────────────────── 100ms ───────│─── 118ms ──── 200ms
                                    │
NPU-ViT: [...正常任务...] BB(SCF_R)─┼──继续跑──┤完成
                                    │          │
                                    │          ▼
                                    │   118ms: 周期 N+1 的任务才开始
                                    │   ┌─ BA(MPIC) 延迟18ms启动
                                    │   ...
```

**后果**：
- 周期 N+1 的所有 NPU-ViT 任务被推迟 18ms 启动
- 周期 N+1 的 deadline 不变（还是 200ms 时刻），但可用时间从 100ms 缩短为 82ms
- 如果连续多轮溢出 → 累积延迟 → 触发降级机制

### Core UC 超时：直接丢弃

```
周期 N                              │  周期 N+1
0ms ────────────────── 100ms ───────│──────── 200ms
                                    │
NPU-ViT: [...safety任务...] uc12推理─┼─ 未完成 → 丢弃！
                                    │
                                    │  0ms: 周期 N+1 正常启动
                                    │  uc12 使用上一轮的结果
                                    │  (stale result, 但 core 可容忍)
```

**设计理由**：
- Core UC 的 `max_latency_ms` 通常较宽松（200~500ms）
- 丢一帧结果（100ms 的数据空白）对 core 功能影响有限
- 不能让 core 的溢出占用下一轮 safety 的时间

## 防止超时的三道防线

系统设计目标是 **让超时尽量不发生**，而不是靠超时处理来兜底：

### 第一道防线：调度前预计算

```
在周期开始前，调度器已经知道本轮要跑哪些任务、总耗时多少。
如果预计算发现会超时 → 主动跳过低优先级任务（不调度）。

例: 本轮已安排 BA(25ms) + BB_FWC(30ms) + BB_SCF_L(30ms) = 85ms
    再加 BB_SCF_R(30ms) = 115ms > 100ms
    → 调度器决定本轮不调度 SCF_R，延到下轮
```

### 第二道防线：降频/交错调度

```
文档方案B: SCF_L/SCF_R 交替调度
  → 每轮最多跑2个 Backbone_B (60ms)，不会3个串行 (90ms)
  → 从设计上保证单周期可完成

轮次   NPU-ViT 安排                      耗时
#1     BA(MPIC) + BB(FWC) + BB(SCF_L)    25+30+30 = 85ms ✅
#2     BA(MPIC) + BB(FWC) + BB(SCF_R)    25+30+30 = 85ms ✅
```

### 第三道防线：动态降级

```
如果连续多轮出现溢出/接近溢出:
  → 调度器触发 degradation 策略
  → core UC 进一步降频 (reduce_fps_to)
  → 或关闭 enhancement UC (disable_entirely)
  → 释放时间余量给 safety UC

触发条件示例:
  连续3轮溢出 → 自动执行:
    uc12: reduce_fps_to 从 2Hz 降到 1Hz
    uc10: reduce_fps_to 从 1Hz 降到 0.5Hz
```

## 如果 Safety UC 自身都超时怎么办

这是最严重的情况。设计上通过 `max_latency_ms` 约束确保正常条件下不会发生：

```
uc17: max_latency_ms = 100
  实际耗时: max(ViT:25ms, CV:22ms) = 25ms → 余量 75ms ✅✅

uc11: max_latency_ms = 100
  优化后: 87ms → 余量 13ms ✅ (较紧但可接受)

uc13: max_latency_ms = 100
  实际耗时: 94ms → 余量 6ms ✅ (非常紧)
```

如果因为意外原因（热降频、NPU 卡顿）导致 safety UC 也超时：

```
处理流程:
  1. 不丢弃 — 溢出执行完毕（safety 结果不能缺失）
  2. 上报异常事件 — 通知系统监控
  3. 连续超时 N 次 → 触发系统级降级:
     ├─ 降低输入分辨率 (1080p → 720p → 540p)
     ├─ 减少输入帧数 (去掉非必要 camera 流)
     ├─ NPU 频率提升 (如果热余量允许)
     └─ 最终兜底: 切换到纯 CV 轻量方案 (放弃 ViT)
```

## 超时与帧同步的关系

```
正常情况:
  周期 N 开始 → 锁存帧 → 执行 → 周期 N 结束
  周期 N+1 开始 → 锁存新帧 → 执行 → ...

Safety 溢出情况:
  周期 N 开始 → 锁存帧 → 执行...
  周期 N 结束(100ms) → safety 任务还在跑 → 继续用周期 N 的帧完成
  溢出完成(118ms) → 周期 N+1 开始 → 锁存新帧（此时帧已经是118ms时刻的）
  
  问: 周期 N+1 的帧比正常晚了 18ms，有影响吗？
  答: 帧本身还是"当前最新帧"，只是整体流水线延迟增加了 18ms。
      对于 10Hz 系统，100ms 采一次帧，18ms 的偏移 < 1帧间隔，可接受。

Core 丢弃情况:
  周期 N 结束(100ms) → core 任务未完成 → 丢弃
  周期 N+1 开始 → 正常锁存新帧 → 不受影响
  → core 丢弃的好处是：不让超时污染下一周期的帧同步
```

## NPU-CV 和 NPU-ViT 分别超时的处理

由于两个 NPU 独立运行，超时可能只发生在一个 NPU 上：

```
情况 A: NPU-ViT 超时，NPU-CV 正常完成
  → NPU-CV 结果正常可用
  → 需要融合(parallel_merge)的 UC：等 NPU-ViT 溢出完成后再融合
  → 纯 CV 的结果可以先输出给不需要融合的下游

情况 B: NPU-CV 超时，NPU-ViT 正常完成
  → NPU-ViT 的 Head 结果正常可用
  → 需要 CV+ViT 融合的 UC：
     safety: 等 CV 溢出完成
     core: 直接用 ViT 结果（CV 部分用上轮值）

情况 C: 两个 NPU 都超时
  → 极端情况，通常意味着系统异常
  → 触发最高级别降级
```

## 总结

| 问题 | 答案 |
|------|------|
| Safety UC 超时 | 溢出到下一周期继续执行，不丢弃 |
| Core UC 超时 | 直接丢弃未完成的任务，用上轮结果补位 |
| 超时是否常态？ | 不是，三道防线保证绝大多数情况不超时 |
| 连续超时怎么办？ | 触发动态降级，释放资源给高优先级 |
| 超时影响帧同步吗？ | Safety溢出会推迟下轮帧锁存；Core丢弃不影响 |
| 设计理念 | 预防为主（预计算+交错），兜底为辅（溢出/丢弃） |
