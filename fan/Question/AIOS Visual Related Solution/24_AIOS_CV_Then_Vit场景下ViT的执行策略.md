# NPU Safety 抢占机制分析：cv_then_vit 场景下 ViT 的执行策略

## 核心问题

在 `cv_then_vit` pipeline 中，两个 NPU 分工：
- **NPU-CV**：执行 CV 模型，产出初筛结果
- **NPU-ViT**：根据 CV 结果决定是否执行 ViT 推理

当 CV 结果触发 safety 级别的 ViT 任务时，NPU-ViT 是直接终止当前任务，还是等当前任务完成？

---

## 结论：队列级抢占，非执行级打断

**等当前 ViT 任务完成，然后立即插到队列最前面执行。**

---

## 原因分析

### 1. NPU 推理是原子操作

一次 Backbone 推理（25~30ms）一旦开始就不能中途打断：
- 硬件上没有"暂停恢复"的能力
- 强行终止会丢失全部中间计算结果
- 重新执行意味着浪费已消耗的时间

### 2. 抢占发生在队列层面，不是执行层面

所谓"立即抢占"是指：
- 当前正在跑的推理正常完成
- Safety 任务跳过队列中所有其他等待任务
- 下一个就执行 safety 的 ViT 任务

### 3. `preemptible=false` 的含义

Safety UC 标记的是 `preemptible=false`，意思是：
- **Safety 任务自己不能被别人抢占**（保证一旦开始执行就能完成）
- **不是说它能打断别人正在执行的推理**

## 时序示意

### 正常情况（NPU-ViT 空闲时 CV 结果到达）

```
时间轴     NPU-CV                         NPU-ViT
────────────────────────────────────────────────────────────
0ms       ┌─ cv_model 执行 ─┐            [空闲]
~15ms     └─ 输出结果 ──────┘
          判断: 需要 ViT ✓
          → 立即调度到 NPU-ViT
~15ms                                    ┌─ safety ViT 执行 ─┐
~45ms                                    └─ 完成 ────────────┘

总延迟: 15ms(CV) + 30ms(ViT) = 45ms ✅ 远低于100ms deadline
```

### 最坏情况（NPU-ViT 正在执行其他任务）

```
时间轴     NPU-CV                         NPU-ViT
────────────────────────────────────────────────────────────
0ms       ┌─ cv_model 执行 ─┐            ┌─ 正在跑 Backbone_B ─┐
          │                 │            │  (已执行了10ms,      │
          │                 │            │   还剩20ms)          │
~15ms     └─ 输出结果 ──────┘            │                     │
          判断: 需要 ViT ✓               │                     │
          → 插入队列最前面               │                     │
          （等待当前任务完成）             │                     │
~30ms                                    └─ 当前任务完成 ──────┘
                                         ┌─ safety ViT 立即执行 ─┐
~60ms                                    └─ 完成 ───────────────┘

总延迟: 15ms(CV) + 15ms(等待) + 30ms(ViT) = 60ms ✅ 仍在100ms内
```

### 绝对最坏情况

```
最坏等待时间 = 一个完整 Backbone 时长 = 30ms
最坏总延迟 = CV(20ms) + 等待(30ms) + ViT(30ms) = 80ms
Deadline = 100ms
裕量 = 20ms ✅
```

---

## 为什么不做执行级打断

| 维度 | 队列级抢占 | 执行级打断 |
|------|-----------|-----------|
| 硬件可行性 | ✅ 软件调度即可 | ❌ NPU无中断恢复机制 |
| 计算浪费 | ✅ 零浪费 | ❌ 已计算结果全部丢失 |
| 实现复杂度 | ✅ 简单优先级队列 | ❌ 需要硬件+驱动支持 |
| 最坏延迟 | ≤30ms额外 | 0ms额外 |
| 能否满足deadline | ✅ 80ms < 100ms | ✅ 50ms < 100ms |

**结论：队列级抢占已经足够满足 100ms deadline，无需引入复杂的执行级打断。**

---

## 调度优化：减少被占位概率

文档中通过以下策略确保 safety 任务"被阻塞等待"的概率最小化：

1. **Safety 相关帧排在队列最前面**
   ```
   NPU-ViT 队列优先级: MPIC(P100) → FWC(P100/P95) → SCF(P100) → FTC(P95)
   ```

2. **降频非 safety 任务**
   - uc12 (P80): 每5轮才主动调度一次
   - uc10 (P80): 每10轮才主动调度一次
   - 减少低优先级任务占用 NPU-ViT 的时间窗口

3. **搭便车机制**
   - 低优先级 UC 标记 `same_backbone_shared=true`
   - 不需要额外的 Backbone 推理，只是复用已有输出的 Head
   - 从根本上减少了对 NPU-ViT 时间片的占用

## 与其他 Pipeline Type 的对比

| Pipeline Type | ViT 执行时机 | 抢占相关性 |
|--------------|-------------|-----------|
| `cv_vit_parallel` | ViT 和 CV 同时启动 | 无依赖，不涉及抢占问题 |
| `only_vit` | 只跑 ViT | 直接按优先级排队 |
| `cv_then_vit` | CV 完成后触发 ViT | **本文讨论场景** |
| `trigger_escalation` | always-on 触发后唤醒 | 与 cv_then_vit 类似机制 |
