这是个很实际的工程约束问题。核心矛盾是：**多路流需要"同时"感知，但 NPU 同一时刻只能推理一张图**。

关键事实：**多路流截帧时间戳是一致的（同步采集），时间差仅由 NPU 串行推理引入，不是真实的时空不一致。** 这意味着不需要时间戳衰减、异步触发等复杂机制。

以下是几种方案，按工程复杂度递增排列：

---

## 方案 1：同步截帧 + 串行推理 + Late Fusion — 推荐首选

```
┌─────────────────────────────────────────────────────────────┐
│  1. 同步截帧 (t0)                                            │
│     FWC / SCF_L / SCF_R 同时抓帧（同一时间戳）                 │
├─────────────────────────────────────────────────────────────┤
│  2. NPU 串行推理（硬件约束）                                   │
│     t0+0ms:  NPU 推理 FWC   → prob_fwc                      │
│     t0+30ms: NPU 推理 SCF_L → prob_scf_l                    │
│     t0+60ms: NPU 推理 SCF_R → prob_scf_r                    │
├─────────────────────────────────────────────────────────────┤
│  3. 结果收齐（写入同一 batch buffer，无需衰减）                 │
├─────────────────────────────────────────────────────────────┤
│  4. Late Fusion 决策 (CPU, <0.1ms)                           │
│     加权平均 / 投票 / 置信度门控 → 最终结果                     │
└─────────────────────────────────────────────────────────────┘
```

**做法：** 所有流同步截帧，NPU 依次推理，各自输出分类概率向量（logits/softmax），全部到齐后在 CPU 上做融合决策。

**融合策略举例：**
```python
# 加权平均（FWC 权重更高，因为正前方是主视角）
weights = {'FWC': 0.5, 'SCF_L': 0.25, 'SCF_R': 0.25}
final_prob = w_fwc * prob_fwc + w_scf_l * prob_scf_l + w_scf_r * prob_scf_r

# 或者置信度门控：只有当 FWC 不确定时才参考 SCF
if max(prob_fwc) < 0.6:
    final_prob = 0.4 * prob_fwc + 0.3 * prob_scf_l + 0.3 * prob_scf_r
else:
    final_prob = prob_fwc
```

**容错逻辑：** 若某路推理异常（超时/硬件错误），用上一轮结果兜底或仅用可用结果做融合。

**相比独立的"时分复用+缓存"方案，省去的复杂度：**

| 不再需要 | 原因 |
|---------|------|
| 时间戳衰减权重 | 帧同步采集，语义上是同一时刻，不存在"过期" |
| 异步触发决策 | 等一轮跑完再决策即可 |
| 缺失结果的降级逻辑 | 除非硬件故障，一轮内必然全部完成 |

**优点：** 最简单、无需改模型、各路流完全解耦、容错性好、无伪时延问题
**延迟：** N × 单帧推理时间（3 路 × ~30ms = ~90ms），对天气/景色等慢变量完全可接受
**适用场景：** 变化慢的分类任务（天气/光照/景色），以及需要多路汇总的场景（停车场景的车位/障碍物检测）

---

## 方案 2：Feature Cache + Fusion Head（特征级融合）

```
t0: FWC  → Backbone → feature_fwc [1×768]  → 存入 cache
t1: SCF_L → Backbone → feature_scf_l [1×768] → 存入 cache
t2: 从 cache 取两个 feature → Concat [1×1536] → Fusion Head → 决策
```

**做法：** 不直接对各路做分类，而是缓存 backbone 输出的 feature vector，拼接后过一个专门的 Fusion Head。

```python
# Fusion Head (极轻量，CPU 即可)
fusion_head = nn.Sequential(
    nn.Linear(768 * 2, 256),  # concat FWC + SCF
    nn.ReLU(),
    nn.Linear(256, num_classes)
)
```

**优点：** 比 Late Fusion 信息量更大（融合的是特征而非概率，保留了更多语义信息）
**缺点：** 特征之间有时间差，且如果 backbone 不同（A vs B），特征空间不一致需要额外对齐

---

## 方案 3：主从架构（Primary-Secondary）

```
优先级调度：
  FWC (Primary)  → 每帧都推理 (10Hz)
  SCF (Secondary) → 低频推理 (2Hz) 或条件触发

决策逻辑：
  - 正常情况：只用 FWC 结果
  - FWC 置信度低 / 边缘case → 调高 SCF 频率，做 fusion
  - FWC 置信度高 → SCF 结果仅做校验，不参与决策
```

**适用场景：** 有明确主次关系的多路流（FWC 是主，SCF 是辅），避免无脑轮询浪费算力。

---

## 方案对比

| 方案 | 延迟 | 精度提升 | 工程复杂度 | 适用场景 |
|------|------|---------|-----------|---------|
| 同步截帧 + Late Fusion | N × 单帧 | 中等 | **低** | 通用首选，变化慢的分类（天气/景色/光照/停车） |
| Feature Fusion | N × 单帧 | **最高** | 高 | 需要跨视角语义理解（如全景景色判断） |
| 主从架构 | 接近单帧 | 中等 | 中 | 有明确主次的场景（FWC 主 + SCF 辅），需压延迟时 |

---

## 我的建议

对于当前的场景组合：

| 场景类型 | 推荐方案 | 理由 |
|---------|---------|------|
| 天气/光照分类 | **方案 3（主从）** | FWC 一路足够判断，SCF 仅在阴影/逆光等边缘 case 辅助 |
| 景色识别 | **方案 1（同步+Late Fusion）** | 景色变化慢（秒级），90ms 串行延迟完全可接受，帧同步无需额外处理 |
| 特殊车辆/手势 | **方案 1 + 方案 3 混合** | 同步截帧保证语义一致，FWC 高频主推 + SCR 低频补盲（后方来车） |
| 停车场景 | **方案 1（同步+Late Fusion）** | 多路 SVC/SCF 各自独立检测车位/障碍物，同步截帧后汇总 |

实际上大多数场景用 **方案 1（同步截帧 + 串行推理 + Late Fusion）** 作为基础框架就够了——帧本身是同步的，NPU 串行只是硬件约束，不引入语义时间差。在此之上对需要压延迟的场景叠加主从策略优化 NPU 利用率。
