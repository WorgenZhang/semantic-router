# NPU 多 UC 并发触发与优先级调度策略

## 核心问题

1. 单周期 100ms 内高优先级 UC 通过 CV 或 ViT 得到结果后被触发了，后续的 UC 还执行吗？
2. 同一个周期内 100ms 两个 UC 同时触发，优先级高的先被触发，优先级低的是直接舍弃还是延迟执行？

---

## 问题 1：高优先级 UC 触发后，后续 UC 还执行吗？

### 结论：还执行

所有在 Step 2 中规则匹配通过的 UC 都会被调度，不存在"一个触发了就跳过其他"的逻辑。

### 原因

1. **UC 之间是独立并行的感知任务，不是互斥的 if-else**

   比如 uc17（舱内感知）和 uc11（手势识别）同时触发，它们检测的是完全不同的事物：
   - uc17：看儿童安全、驾驶员疲劳
   - uc11：看交警手势、行人手势
   
   两者结果都需要，缺一不可。

2. **文档明确列出了 8 个 UC 同时激活的执行方案**

   Step 5 输出中 uc17/uc11/uc13/uc12/uc10/uc5 全部同时激活运行，而非只选一个。

3. **资源不够时的处理是降频/降级，不是"高优先级触发就丢弃低优先级"**

   ```
   uc12 (P80): 10Hz → 降到 2Hz（还在跑，只是频率低了）
   uc10 (P80): 2Hz  → 降到 1Hz（还在跑）
   uc8  (P40): disable_entirely（完全关闭）
   uc3  (P40): disable_entirely（完全关闭）
   ```

### 关键区分

被 disable 的 uc8/uc3 是因为 **NPU 负载超 70% 上限**，不是因为"uc17 先触发了所以轮不到你"。

如果系统负载允许（比如激活的 UC 数量少、HIGH_POWER 模式），所有匹配通过的 UC 都能全频率运行。

---

## 问题 2：两个 UC 同时触发，低优先级是舍弃还是延迟？

### 结论：既不是简单舍弃也不是简单延迟，而是分层递进处理

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 情况                              │ 处理方式                             │
├──────────────────────────────────────────────────────────────────────────┤
│ 两个 UC 不争抢同一 NPU 资源       │ 完全并行执行，互不影响               │
│ (例: 一个用 NPU-CV,              │                                      │
│  一个用 NPU-ViT)                 │                                      │
├──────────────────────────────────────────────────────────────────────────┤
│ 两个 UC 争抢同一 NPU 但           │ 高优先级先执行，低优先级排队等待     │
│ 总时间在 100ms 内能完成           │ 同一周期内都能拿到结果               │
│                                   │ （延迟执行，不舍弃）                 │
├──────────────────────────────────────────────────────────────────────────┤
│ 两个 UC 争抢同一 NPU 且           │ 低优先级被降频                       │
│ 总时间超出单周期                  │ 本轮跳过，下几轮再调度               │
│                                   │ （不是永久舍弃，是降频调度）         │
├──────────────────────────────────────────────────────────────────────────┤
│ 系统资源严重不足                  │ enhancement tier 被 disable          │
│ (NPU负载超限)                     │ （完全舍弃，直到资源恢复）           │
└──────────────────────────────────────────────────────────────────────────┘
```

### 具体场景分析

#### 场景 A：共享资源，零冲突

uc17 (P100) 和 uc5 (P75) 同时触发，都需要 MPIC 帧：

```
共享 Backbone_A 输出 → 不存在争抢
  uc17 拿 head_a2 + head_a3 + head_a4
  uc5  拿 head_a2 + head_a3
→ 两个都在 25.3ms 内拿到结果，零冲突
```

#### 场景 B：共享 Backbone，降频调度

uc11 (P100) 和 uc12 (P80) 同时触发，都需要 Backbone_B：

```
same_backbone_shared=true → 共享同一次 Backbone_B 推理
  uc11 拿 head_b3 (特殊车辆)
  uc12 也拿 head_b3 (特殊车辆)
→ 零冲突，uc12 只是调度频率被降到 2Hz（每5轮调度一次）
  但每次调度都能复用 uc11 已跑完的 Backbone_B 输出
```

#### 场景 C：多路帧串行，交错延迟

uc11 需要 FWC + SCF_L + SCF_R 三路帧都过 Backbone_B：

```
FWC:   每轮都跑（P100 主路）
SCF_L: 奇数轮跑（延迟到本轮）
SCF_R: 偶数轮跑（延迟到下轮）
→ SCF_R 不是被舍弃，而是交错到下一周期执行
  融合时用上轮结果补位，通过 weights 补偿时间偏移
```

#### 场景 D：资源超限，完全关闭

uc8 (P40) 和 uc3 (P40) 在 NPU 负载超限时：

```
degradation.disable_entirely: true
→ 完全关闭，不调度，不占资源
→ 直到负载降低（其他 UC 退出）时才恢复
```

## 调度优先级递进处理总结

```
                    匹配通过的 UC 列表
                         │
                         ▼
              ┌─────────────────────┐
              │ 1. 能共享就共享     │  same_backbone_shared=true
              │    零额外开销       │  多个 UC 复用同一 Backbone 输出
              └──────────┬──────────┘
                         │ 共享不够，还有冲突
                         ▼
              ┌─────────────────────┐
              │ 2. 能排队就排队     │  同一周期内串行执行
              │    高优先级先跑     │  低优先级等一等但本轮拿到结果
              └──────────┬──────────┘
                         │ 排队也装不下（超 100ms）
                         ▼
              ┌─────────────────────┐
              │ 3. 降频调度         │  reduce_fps_to: N
              │    不是每轮都跑     │  本轮跳过，隔几轮再执行
              └──────────┬──────────┘
                         │ 降频还是装不下（NPU 负载超限）
                         ▼
              ┌─────────────────────┐
              │ 4. 完全关闭         │  disable_entirely: true
              │    让出全部资源     │  仅对 enhancement tier 生效
              └─────────────────────┘
```

## 与"互斥触发"系统的对比

| 维度 | 互斥触发（传统方式） | 并行调度（本系统） |
|------|---------------------|-------------------|
| 同时匹配多个 UC | 只选最高优先级的一个 | 全部激活，分层处理 |
| 低优先级 UC 命运 | 直接丢弃 | 共享/排队/降频/最后才disable |
| 结果完整性 | 只有一个 UC 的结果 | 多个 UC 并行产出结果 |
| 适用场景 | 简单系统、单 NPU | 多 NPU、多传感器融合 |
| Safety 保证 | 高优先级保证执行 | Safety tier 全部保证执行 |

---

## 关键设计原则

1. **Safety tier 之间不互斥** — uc17/uc11/uc13 全部是 P95~P100，它们之间永远共存，不存在"uc17 触发了 uc11 就不跑"的情况

2. **同 tier 不抢占** — 同为 safety 的 UC 之间不互相抢占，通过 Backbone 共享和 NPU 并行同时服务

3. **跨 tier 才有让步** — 只有当 core/enhancement tier 与 safety tier 争抢资源时，才会发生降频或关闭

4. **让步是渐进的** — 降频优先于关闭，关闭是最后手段且仅对 enhancement tier 生效
